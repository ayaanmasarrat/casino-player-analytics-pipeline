# Methodology

This document describes the analytical methods used in the Casino Player
Analytics Pipeline.  All examples and numbers below come from the synthetic
dataset generated by `synth/generate.py`.

---

## 1  Data Overview

The pipeline ingests four CSV tables:

| Table | Grain | Key columns |
|---|---|---|
| `play_by_month.csv` | Transaction | `player_id`, `accounting_date`, `coin_in`, `theo_win`, `actual_win`, `game_type` |
| `players.csv` | Player (one row per player) | `player_id`, `date_of_birth`, `gender`, `state`, `zip`, `zip_lat`, `zip_lon`, `enrollment_date` |
| `jackpots.csv` | Jackpot event | `player_id`, `jackpot_date`, `amount` |
| `app_events.csv` | App adoption | `player_id`, `adoption_date` |

---

## 2  Feature Engineering

### 2.1  Daily Player Level

Raw transactions are merged with player demographics on `player_id` and then
aggregated to one row per `(player_id, accounting_date)`.  Aggregation:

- `coin_in`, `theo_win`, `actual_win` → **sum**
- `n_txn` → **count** of raw transactions
- `game_type` → **mode** (most frequent game that day)

All other demographic columns are carried forward via `first()`.

### 2.2  Age at Visit

Exact age in completed years is computed with a vectorised formula:

```
years_diff = visit_year − dob_year
not_yet    = 1 if (visit_month, visit_day) < (dob_month, dob_day) else 0
age        = years_diff − not_yet
```

Players are then assigned to one of seven age buckets:
21–29, 30–39, 40–49, 50–59, 60–69, 70–79, 80+.

### 2.3  Hold Percentages

```
theo_hold_pct  = theo_win  / coin_in × 100
act_hold_pct   = actual_win / coin_in × 100
```

Both are set to `NaN` when `coin_in < 1.0` (configurable via `SETTINGS`) to
prevent divide-by-zero artefacts.

### 2.4  Distance and Mileage Band

The haversine formula computes straight-line distance (in miles) from each
player's home ZIP centroid to the venue.  Bands:

| Band | Definition |
|---|---|
| Local | < 30 miles |
| Regional | 30 – 150 miles |
| National | > 150 miles |

### 2.5  Player Rollup

Players are aggregated to lifetime metrics:

- **AMV** (Average Monthly Value) = `total_coin_in / active_months`
- **ADT** (Average Daily Trips) = `n_visit_days / active_months`
- `active_months` = span from first to last visit (minimum 1)

### 2.6  Player-Month Panel

A balanced panel of `(player_id, year, month)` rows is built from the daily
table by grouping on year and month.  This is the primary unit of analysis
for the causal models.

## 3  Segmentation

### 3.1  L1 — Value Tier

Based on AMV:

| Tier | Condition |
|---|---|
| High | AMV ≥ $500 |
| Medium | $150 ≤ AMV < $500 |
| Low | AMV < $150 |

### 3.2  L2 — Activity Tier

Based on total distinct visit days:

| Tier | Condition |
|---|---|
| Frequent | ≥ 8 visit days |
| Occasional | 3 – 7 visit days |
| Lapsed | < 3 visit days |

---

## 4  Trend Analytics

Monthly Active Users (MAU) is the count of distinct `player_id` values active
in each calendar month, optionally broken out by L1 segment.

Year-over-year (YoY) comparison merges MAU with a one-year-lagged version of
itself to compute `mau_yoy_pct` and `coin_yoy_pct`.

---

## 5  Causal Inference

The causal section estimates the effect of mobile-app adoption on player
spending.  This is an observational study, so treated and control players
differ systematically.  We use propensity-score matching (PSM) to construct
a comparable control group, then a difference-in-differences (DiD) estimator
to identify the causal effect.

### 5.1  Propensity Score Estimation

A logistic regression predicts the probability of app adoption from
pre-treatment covariates: `amv`, `adt`, `n_visit_days`, `distance_miles`.
Features are standardised with `StandardScaler` before fitting.

### 5.2  Common Support Trimming

Observations outside the common support region (bottom and top 1 % of the
treated propensity distribution) are dropped to avoid extrapolation.

### 5.3  1:5 Nearest-Neighbour Matching

For each treated player, up to 5 control players within a 0.05 propensity
caliper are selected without replacement.  Controls are chosen via a
sorted-array binary search (O(log n) per treated unit).

### 5.4  Covariate Balance

Standardised mean difference (SMD) is computed for each covariate before and
after matching:

```
SMD = (mean_treated − mean_control) / sqrt((sd_treated² + sd_control²) / 2)
```

A Love plot visualises balance improvement.  |SMD| < 0.10 after matching
indicates adequate balance.

### 5.5  Difference-in-Differences

Two OLS specifications are estimated on the matched sample:

**Basic DiD**
```
coin_in_it = α + β₁·treated_i + β₂·post_t + β₃·(treated × post) + ε_it
```

**DiD with month fixed effects**
```
coin_in_it = α_t + β₁·treated_i + β₃·(treated × post) + ε_it
```

Both models use standard errors clustered at the `player_id` level.
The coefficient β₃ is the Average Treatment Effect on the Treated (ATT).

### 5.6  Event Study and Parallel Trends Test

Relative-time dummies (months since adoption) replace the single `post`
indicator.  The omitted period is month −1 (one month before adoption).

Pre-treatment coefficients are jointly tested (F-test) for equality to zero.
Failure to reject at α = 0.05 is consistent with the parallel-trends
assumption.

## 7  Synthetic Data Caveats

All results in this repository are produced from a **seeded synthetic dataset**.
The generator (`synth/generate.py`) deliberately injects selection bias into
the treatment-adoption process (treated players skew younger and higher AMV)
so that the PSM and DiD machinery has something real to do, but the numbers
do not represent any real venue or player population.
